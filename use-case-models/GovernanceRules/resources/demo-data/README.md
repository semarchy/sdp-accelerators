# GovernanceRules - demo data

Test dataset of the **GovernanceRules** data product: a referential of 71 data governance rules
(56 generic + 15 for a pharma extension) with the policies, governance bodies, regulations and
standards, data domains, data classifications and business attribute types they refer to, plus
three deliberately invalid rules that show the validations at work.

Use it to:

- see the data product with realistic content right after a deployment (rules by category,
  coverage matrix, the Rule review workflow on drafts and rules in review);
- demonstrate an AI design agent that reads the rules through the data product's MCP server and
  only ever sees the rules **in force**;
- show stewardship of records in error after the first certification.

All content is synthetic or public: rule texts were written for this accelerator, regulations
and standards are cited by their public references, governance bodies use `@example.com`
addresses, and the only user name is the fictional `governance.owner`.

## Column conventions

- Header = the SEML attribute names (`Code`, `Title`, `LifecycleStatus`, ...).
- A reference is a `FID_<role>` column holding the **code** of the referenced record:
  `FID_OwnerBody` (GovernancePolicy, GovernanceRule), `FID_Policy` (GovernanceRule),
  `FID_DefaultClassification`, `FID_ReferenceStandard` (BusinessAttributeType),
  `FID_Rule`, `FID_DataDomain`, `FID_DataClassification`, `FID_AttributeType` (RuleScope),
  `FID_Rule`, `FID_Regulation` (RuleCitation).
- No `ID` column in RuleScope and RuleCitation: the ID is generated by a sequence when the record
  is loaded.
- No `InForce` column: the `ComputeInForce` enricher computes it at certification.
- Lists of values hold the code (`MUST`, `APPROVED`, `DATA_QUALITY`, ...).
- UTF-8 without BOM, comma separator, values quoted only when needed, LF line ends.
  Dates `yyyy-MM-dd`; booleans `true` / `false`; an empty cell is a null.
- In the JSON payload the same names are used and null attributes are omitted.

## Storyline

**Rules and their lifecycle.** Each rule is an RFC 2119 statement (MUST / SHOULD / MAY) in one of
ten categories, with its implementation pattern (validation, enricher, row filter, workflow, ...),
guidance and an example. Its scope rows say where it applies (*data domain + data classification +
attribute type*, an empty dimension meaning "any"; 24 rows with all three empty make their rule
apply everywhere); its citations point to the clause of the regulation or standard it implements.

| Status | Rules | Codes | In force |
|---|---|---|---|
| APPROVED | 65 | all others | yes (effective dates 2024-09-01 to 2025-09-01) |
| DRAFT | 2 | PRIV-008, MOD-005 | no (effective 2027-01-01, not approved) |
| IN_REVIEW | 2 | MDM-005, AI-005 | no (waiting for the governance owner in the Rule review workflow) |
| RETIRED | 2 | DQ-007 (superseded by DQ-005), RET-005 (replaced by RET-001 and RET-003) | no (retirement date passed; `RetirementReason` filled) |

**What an AI agent role does not see.** The `GovernanceAgent` role (the MCP client of a design
agent) has row filters on GovernanceRule, RuleScope and RuleCitation: it reads only rules that are
APPROVED, effective and not retired, with their scopes and citations. Of the 71 certified rules it
sees **65**, with **126** of the 133 scope rows and **139** of the 146 citations; the two drafts,
the two rules in review and the two retired rules never reach a design. Stewards
(`GovernanceSteward`) and the owner (`GovernanceOwner`) see everything.

**Demo path.** The corpus includes the rules a design agent should find when it adds a
cross-domain attribute to Customer and Product models: country codes against a managed
ISO 3166-1 reference (REF-001, MOD-004), product descriptions in each market's official languages
(DQ-006, REF-003), documentation of every attribute for people and AI agents (META-001,
META-002), personal data hidden from roles without a need to know (PRIV-001, PRIV-002, AI-004).
`source/CORPUS.md` lists them all.

## Pharma extension

Fifteen rules (codes `xx-1nn`, policy **POL-GXP**, owner **GXPQA**) cover GxP and health data:
21 CFR Part 11, EU GMP Annex 11, HIPAA, NPI, the Physician Payments Sunshine Act (Open Payments),
NDC, ISO IDMP (ISO 11615 / 11616). They come with three pharma data domains (MEDICINAL_PRODUCT,
HCP, CLINICAL_SITE), six pharma attribute types (NDC, NPI, HCP_LICENSE_NUMBER, MPID, PHPID,
TRANSFER_OF_VALUE), the PHI classification and eight regulations cited only by them.

**Scoping.** Every one of the 32 scope rows of a pharma rule names a pharma domain or a pharma
attribute type, and no generic rule is scoped to one: a design outside pharma never receives a
pharma rule, while a pharma design receives both the generic rules and the extension. The
validator enforces this. To ship without the extension, delete the POL-GXP rules (and, if
wanted, the pharma domains, attribute types, PHI and regulations) from `source/` and update the
expected counts in `tools/validate_demo_data.py`.

## Deliberate validation failures

Three GovernanceRule rows, appended after the corpus and titled `[DELIBERATE FAILURE] ...`,
each fail exactly one check. No scope or citation references them.

| Code | Fails | Why |
|---|---|---|
| `DQ-BAD1` | validation **RetirementAfterEffective** | RETIRED, effective 2026-01-01 but retirement date 2025-01-01 |
| `DQ-BAD2` | validation **ApprovedRuleHasScope** | APPROVED and effective, but no scope row |
| `DQ-BAD3` | mandatory attribute **Statement** | DRAFT with an empty statement |

All checks run in the pre-consolidation scope: the three records are rejected and not certified;
the rest of the load is certified normally. Remove them by emptying the array in
`source/_deliberate-failures.json` (then update `EXPECTED_*` in the validator).

## How to regenerate

Edit the JSON files in `source/` (keep `source/CORPUS.md` in step), then, from any folder:

```bash
python resources/demo-data/tools/build_demo_data.py      # writes data-files/ and the API payload
python resources/demo-data/tools/validate_demo_data.py   # exit code 0 = ready to load
```

Both scripts need Python 3.9+ and the standard library only (the validator uses PyYAML when it
is installed, otherwise its own minimal parser of the SEML files). The build is deterministic:
`build_demo_data.py --check` fails when a generated file is out of date. The validator reads the
model from `src/GovernanceRules` (option `--seml-root`), evaluates the in-force logic as of today
(option `--as-of yyyy-MM-dd`), and compares the result with the expected counts written at the top
of the script: update them, and this README, when the content changes. Optionally, check the
payload with the Semarchy data product plugin: `sdp-bridge load check "<payload>"
--data-product-folder src/GovernanceRules`.
